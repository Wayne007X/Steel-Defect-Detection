# 钢材缺陷检测项目：五阶段完整脉络与模型选择总结

整理日期：2026-11-01。依据：项目负责人补充的开发顺序、现有仓库代码与报告、两轮调优记录，以及新协议的 Val、Test 和工程交付材料。

本文按“基于什么 → 做了什么 → 用什么指标判断 → 最后选择什么”梳理项目，帮助读者看清模型和系统如何一步步发展。它是项目过程总结，不替代原始实验记录，也不修改任何冻结配置或成绩。

## 先看完整主线

**YOLOv8n 训练与 Streamlit 原型 → 早期多项模型对照 → ONNX 与前后端部署 → 两轮精度优先调优 → 新协议重训、统一 Test 与新版交付。**

五个阶段分别回答五个问题：

1. 能否训练出一个模型，并通过网页使用它？
2. 哪些训练策略值得保留，应选择哪个单模型？
3. 如何把模型接成前后端分离、可以部署的检测系统？
4. 在已有模型基础上，怎样进一步提高检测精度并处理误报／漏检取舍？
5. 前面的经验能否在固定、可追溯的评估流程下重新验证，并形成有完整依据的交付？

其中，训练、选型、验证、部署是不同任务。导出 ONNX 或接入网页，不等于又训练了一套精度更高的模型；模型有预测框，也不等于所有缺陷都正确检出。

## 指标怎么读

- **mAP@0.5，简称 AP50／mAP50**：在匹配 IoU=0.50 条件下，综合置信度曲线评价六类检测能力。
- **mAP@0.5:0.95，简称 AP50-95／mAP50-95**：综合多个匹配 IoU 阈值，对框的位置和范围要求更严格。
- **Precision，精确率**：检出的目标中，有多少正确，主要反映误报代价。
- **Recall，召回率**：真实目标中，有多少被检出，主要反映漏检情况。
- **F1**：精确率和召回率的调和平均，用于观察一个工作点的平衡。
- **TP／FP／FN**：分别为正确匹配、未匹配预测和未匹配真实目标。

AP 与固定工作点指标要分开：本轮新协议的 AP 使用低候选阈值完整预测计算；conf=0.25、0.35、0.50 等是另行统计 P/R/F1 的工作点。NMS IoU 用于预测框抑制，匹配 IoU 用于预测与 GT 对照，二者不是同一参数。

早期标准验证的 P/R 来自其验证流程的 PR 曲线工作点，也不能直接标成网页 conf=0.25 的实测 P/R。

## 第一阶段：初次训练与 Streamlit 原型

### 基于什么

使用 YOLOv8n 和 NEU-DET，先完成最基础的目标检测训练、验证与权重保存，再把模型接入 Streamlit，形成最初可以上传图片并查看检测结果的网页原型。

权重文件统一记为 **best.pt**。仓库早期 `app.py` 直接加载 `runs/neu_defect_train/weights/best.pt`，由 Streamlit 应用自己调用 YOLO 推理；这一版没有独立 FastAPI 推理后端。

### 做了什么、怎样判断

基本链路是：准备数据 → 训练 YOLOv8n → 验证 → 保存最佳权重 → Streamlit 加载权重 → 上传图片并绘制检测框。

主要检查模型能否完成训练、权重能否加载、图片能否被检测、结果能否在网页展示。训练损失和验证指标辅助观察训练过程，但这一阶段还不是后续完整的模型选型和固定 Test 验收。

### 最后选择什么

使用当时训练得到的 best.pt 跑通应用原型，取得“模型可以通过网页使用”的初步成果。

现有历史索引还记录了早期数据整理问题及后续纠正。因此，neu_defect_train 应作为早期原型和过程证据保留，不与纠正数据后的 clean／mosaic000 当成同条件公平对照。本文不为最初原型补写未经核实的精度成绩。

证据：[早期 app.py](../app.py)、[早期模型与数据问题记录](../experiments/neu_det_tuning/EXPERIMENT_INDEX.md)。

## 第二阶段：早期多项调优，确定 clean 与 mosaic000 的角色

### 基于什么

在数据整理问题纠正后，使用原来的 **1,440 张 Train＋360 张 Val**，继续比较 YOLOv8 训练策略与候选模型。原 Val 有 854 个标注目标，已经参与模型选择和参数探索。

这一阶段是对初版模型路线的改进，不能把所有尝试都称为只改变一个因素的严格消融实验。

### 做了哪些对照

- Mosaic：比较 1.0、0.5、0 等设置。
- 模型规模：比较 YOLOv8n 与 YOLOv8s。
- 输入尺寸：包括 800 输入微调，以及同一权重 640／800 验证复核。
- 损失与采样：包括 cls、box 权重、龟裂加权采样。
- 优化策略：包括学习率及优化器变化。
- 推理后处理：包括固定置信度／NMS 工作点比较，以及划痕重复框过滤。

受控对照、组合策略、诊断脚本分别记录。有脚本不等于已经完成训练，运行完成也不等于达到验收要求；未通过的尝试继续保留。

### 主要指标是什么

纠正后的两个主要候选，旧标准验证结果为：

- **clean**：Precision 67.31%，Recall 64.95%，mAP50 **72.81%**，mAP50-95 **38.44%**。
- **mosaic000**：Precision 66.39%，Recall 68.86%，mAP50 **72.60%**，mAP50-95 **37.84%**。

clean 的两个 mAP 指标更高；mosaic000 的召回高约 **3.91 个百分点**，但精确率略低。这体现的是误报／漏检取舍，不能描述成 mosaic000 全面优于 clean。

更大模型、部分权重调整和采样策略没有提供足够证据替换主线。记录也不支持简单地认为“提高分辨率就一定更好”。

### 最后根据什么选择了什么

**clean 保留为整体 mAP 基线，mosaic000 保留为偏召回应用候选，输入主线保留 640。**

其中选择 mosaic000 进入后续应用路线，主要考虑它在旧验证记录和固定工作点比较中找回了更多真实目标，符合当时偏向减少漏检的目标；代价是需要接受并复核更多误报。

证据：[实验索引与完整对照](../experiments/neu_det_tuning/EXPERIMENT_INDEX.md)、[早期模型调优报告](../reports/NEU-DET_model_tuning_report.md)、[三模型标准验证记录](../deployment_model_comparison/three_model_standard_metrics.csv)。

## 第三阶段：ONNX、FastAPI、DeepSeek 与 Streamlit 前后端部署

### 基于什么

基于第二阶段保留的 **mosaic000**，把 PyTorch best.pt 导出为 ONNX，推进从“Streamlit 直接加载模型”到“独立后端推理服务＋前端调用接口”。

这一阶段主要解决模型如何部署和使用，不是又得到了一套新的高分训练权重。

### 做了什么

- ONNX Runtime：负责本地／服务端的 ONNX 视觉推理。
- FastAPI：提供健康检查、图片检测和结构化结果。
- Streamlit：上传图片、传递参数、调用 API 和绘制结果。
- DeepSeek：作为独立、按需启用的辅助分析，读取检测结果 JSON，不读取原图、不修改检测框。
- 云端部署：分别部署后端和前端，保留纯视觉检测；云端关闭 AI 调用，本地可显式开启。

### 怎样判断能否继续部署

这里同时关注两个层面：

1. **模型选择层面**：继续沿用前一阶段偏召回的 mosaic000。
2. **工程验证层面**：确认 ONNX 可加载、CPU 可推理、同条件 predict() 数值对照接近，以及 API／网页链路可用。

当时的记录保留了 PyTorch／ONNX 原生 val() 指标差异，尚未彻底解释。不能把“导出成功”和“接口成功响应”写成“全部精度完全一致”，也不能拿一张成功图片代表全数据集效果。

### 最后根据什么选择了什么

**以 mosaic000 ONNX 作为当时的 CPU 部署候选，完成 FastAPI＋Streamlit 前后端链路，并提供本地可选 DeepSeek 分析。**

选择依据是前期召回取舍与已有导出／推理验证证据。旧 GIF、云端测试和截图对应这个阶段，不是后来新协议融合模型的精度或速度证明。

证据：[ONNX 排查及部署决策](../onnx_fast_api_streamlit_docs/MOSAIC000_ONNX_导出与验证排查记录_补充部署决策.md)、[前后端与云端部署记录](../cloud_deployment/钢材缺陷检测系统_云端部署过程记录.md)、[历史 README 展示与验收](history/README_20261030.md)。

## 第四阶段：两轮精度优先调优，形成融合与 TTA 方案

### 基于什么

基于已有 clean／mosaic000 权重，仍使用原来的 **1,440／360** 划分，继续追求精度、检查弱类别并验证部署实现。这时尚未重建固定 Test。

首先统一方形输入等评估设置，重新验证原模型。此配置下，旧 mosaic000 AP50 为 **70.18%**。它与第二阶段旧标准验证的 72.60% 使用不同评估条件，不能混算提升。

### 第一轮做了什么

从旧 mosaic000 出发，以较小学习率和温和的亮度／缩放／平移扰动进行纹理保留微调；再比较新模型与 clean 的融合、TTA 和不同 NMS 策略。

统一复核后：

- 原 mosaic000 单模型：mAP50 **70.18%**，mAP50-95 **36.05%**。
- 纹理单模型 seed42：mAP50 **72.54%**，mAP50-95 **37.00%**。
- clean＋纹理模型＋TTA 平衡方案：mAP50 **76.71%**，mAP50-95 **38.37%**。
- CPU ONNX 融合、无 TTA：mAP50 **75.46%**，mAP50-95 **39.75%**。

单模型微调通过预设的 mAP50-95 改善及逐类退步限制；融合／TTA 提供了进一步的系统方案收益。融合不是单个 YOLOv8n 权重自身达到 76.71%。

### 第二轮做了什么

补做 seed7／123 的纹理微调，三个种子 AP50 为 **72.54%、72.38%、72.14%**，平均约 **72.36% ± 0.20 个百分点**。它们从同一旧 mosaic000 起点微调，不是从通用预训练完整重训三套基线，也不是交叉验证。

同时对弱类别生成对照图，比较类别差异化 NMS；亮度归一化没有通过验收，不采用。类别 NMS 的实际旧 Val 结果为：

- 平衡方案：AP50 **76.71%**；conf=0.25 时 TP/FP/FN 为 **619／211／235**。
- 可选召回方案：AP50 **78.37%**，AP50-95 **39.16%**；相同工作点 TP/FP/FN 为 **633／243／221**。

召回方案多检出 14 个目标，也增加 32 个误报，Precision 下降、Recall 上升、F1 略降。因此不能只因为 AP50 更高就说它在所有用途下都更好。

### 最后根据什么选择了什么

**保留 clean＋纹理模型＋TTA 的平衡方案，另提供召回后处理选项；CPU 保留经过验证的无 TTA 融合。**

本阶段的价值是得到可重复的纹理微调收益、发现模型互补性，并明确精度／召回／误报／速度的取舍。所有成绩仍是参与过选型的旧 Val 探索结果，不能当成独立 Test 成绩。

证据：[第一轮调优报告](../reports/accuracy_tuning_20261030/第一轮调优报告.md)、[第二轮调优报告](../reports/accuracy_tuning_20261030/第二轮调优报告.md)、[两轮综合总结](../reports/accuracy_tuning_20261030/两轮调优综合总结.md)。

## 第五阶段：新协议、受控重训、统一 Test 与新版工程落地

### 为什么需要这一阶段

前面的方法、模型和后处理已经利用旧 Val 反复探索。继续在相同 Val 上追求更高分，难以说明方案在固定新协议下的表现。

因此，这一阶段的重点是重新建立可复核的评估和选择流程，验证前面形成的经验，而不是承诺一定超过旧验证最高分。

### 基于什么重新训练

对现有 NEU-DET 全部 1,800 张图进行审计，以完全相同像素、63 位 pHash 候选、SSIM 辅助和人工决定建立相似性组；固定 Train／Val／Test 为 **1,081／360／359 张**。

共有 1,793 个相似性组，其中 7 个双图组，组不跨集合。相似性组不能宣称是真实钢板／批次组。原始 4,189 行框标注保留；固定框架在读取时去除 3 行重复框后，有效框数为 4,186，其中 Val 808、Test 858。

A／B 从固定官方 COCO 通用预训练重新训练，不使用已见过这些图片的旧 NEU 权重。每组种子固定 **42、7、123**，共 12 个任务：

- **A：标准增强基线**，Mosaic=1，最后 10 轮关闭。
- **B：关闭 Mosaic 对照**，其他基础训练设置与 A 相同。
- **C：温和纹理微调**，从本轮同种子 B 最佳权重开始。
- **D：额外训练控制**，从与 C 完全相同的 B 检查点开始，保持 B 增强，采用与 C 相同的微调优化器、最大轮数及早停规则。

**A／B／C 不是旧 clean／mosaic000／texture 改名。** 训练起点和数据划分均已重建。最佳权重和早停依据 Val AP50，而非库默认的 AP50-95 选择逻辑。

### 在 Val 上得到什么、如何选择

保存权重统一重新评估后，三个种子的平均 Val 结果为：

- A：AP50 **71.78%**，AP50-95 **39.01%**。
- B：AP50 **70.77%**，AP50-95 **36.19%**。
- C：AP50 **73.05%**，AP50-95 **38.88%**。
- D：AP50 **72.06%**，AP50-95 **37.91%**。

C 比 D 的平均 AP50 高约 0.99 个百分点，支持这套温和增强配方在当前条件下的收益；D 也比 B 提高，说明额外训练本身同样可能带来收益。不能把 C−B 全部归因于增强，也不能凭三个种子宣称统计显著。C/D 实际早停轮数不同，属于相同最大预算和停止规则下的配方比较。

**执行偏差：** C/D 实际均保留水平翻转 fliplr=0.5，与原文字“其余几何增强关闭”不完全一致。该差异在 Test 开封前披露，用户确认保留、不重训，原冻结记录没有追溯修改。不能声称完全按原文字方案执行，也不能声称已经证明翻转没有影响。

随后只在预登记候选池中比较单模型、A+B／A+C 融合、TTA 和三种 NMS 策略；工作点只搜索已约定的共享阈值，不开放式调参：

- **研究主方案**：依据三个种子的平均 Val AP50 与预设晋级门槛选择。最终为 **A+C＋TTA，NMS 0.70**，平均 Val AP50 **75.84%**、AP50-95 **42.70%**。
- **平衡模式**：依据平均 Val F1 选择，最终为 A+C＋TTA、顺序 NMS 0.70→0.30，工作点 conf=0.35。
- **召回模式**：在相对平衡模式的 Precision／F1 损失约束下选择最高平均 Val Recall，最终使用类别差异化 NMS，工作点 conf=0.35。

### 冻结后，Test 最终得到什么

固定模型、配置、代码、阈值和测试行，经过人工确认后开封 Test。统一执行 **11 项×3 个种子，共 33 条结果**，全部归档，不根据 Test 调阈值、挑种子或更换主方案。

Val 预先选定的研究主方案，Test 三种子结果为：

- **mAP50：77.19% ± 0.50 个百分点。**
- **mAP50-95：44.73% ± 0.10 个百分点。**

Val 预先选定的两个应用模式，在各自固定工作点的 Test 三种子均值为：

- **平衡模式，conf=0.35**：Precision **79.02%**，Recall **70.98%**，F1 **74.76%**。
- **召回模式，conf=0.35**：Precision **77.72%**，Recall **72.26%**，F1 **74.87%**。

这里的 ± 是三个训练种子的样本标准差，不是置信区间。研究主方案的 conf=0.50 仅用于其固定工作点 P/R/F1，不用于裁剪 AP；它与应用平衡模式的第二级 NMS 和工作点不同，不能拼成一行假称同一配置。

召回模式的 Test AP50 约 77.61%，但不能因为它在 Test 上更高就改称为事先选定的研究主方案。研究选型已经由 Val 冻结。

本轮 C 原生单模型的 Test 平均 AP50 为 **72.50%**，AP50-95 为 **39.96%**。研究主方案的 77.19% 来自双模型融合＋TTA，不是一个单模型权重的成绩。

### 最后如何工程落地

把本轮已训练模型接入独立本地网页，固定使用 seed42，不再额外训练：

- GPU 平衡模式和 GPU 召回模式：A+C seed42＋TTA。
- CPU 融合：A+C ONNX，无 TTA。
- CPU C 单模型：C ONNX，无 TTA。
- 旧模型回退：原 mosaic000 ONNX，原服务继续保留。

新版独立使用 API 8002、网页 8503；没有自动替换旧本地服务或云端。五种模式用 Val 样本完成实际 HTTP 上传和前端交互检查，含“GPU→旧模型→GPU”回切。前端交互使用 AppTest 测试对象驱动，不是浏览器 GUI 自动化；未发送付费 AI 请求。

本轮 Val 单图中位耗时：GPU 平衡约 **76.31 ms**，CPU C 单模型约 **119.26 ms**，CPU 无 TTA 融合约 **234.32 ms**。它们不是完整网页端到端延迟，也不能与旧实验耗时直接算加速倍数。ONNX 是无 TTA 变体，不能把 GPU TTA 精度与 CPU 速度拼成一个方案。

另外生成固定 seed42 平衡工作点的 124 张弱类对照图，覆盖龟裂和氧化铁皮压入的全部 FN/FP。此诊断发生在 Test 后，不能据此改参数，再把同一 Test 当作未参与调优的新测试。

**网页 seed42 的单独成绩与三个种子均值分别报告。** 原始标签、模型、冻结记录和 Test 归档保持不变。

## 五个阶段最后分别留下了什么

1. **第一阶段留下原型**：训练 best.pt，并通过 Streamlit 使用模型。
2. **第二阶段留下候选与选择依据**：clean 作整体 mAP 基线，mosaic000 作偏召回候选，保存有效和失败的对照。
3. **第三阶段留下部署链路**：以 mosaic000 ONNX 跑通 FastAPI＋Streamlit，以及本地可选 DeepSeek、云端纯检测。
4. **第四阶段留下精度优先方案**：纹理微调、clean＋纹理融合＋TTA、平衡／召回选项，以及对误报代价的明确记录。
5. **第五阶段留下固定协议结论与新版交付**：重建 A/B/C/D、三种子 Val 选型、冻结后统一 Test、完整归档和固定 seed42 的新版应用。

## 当前应该如何表述模型结论

研究报告以 **新协议下 Val 预先选定、Test 检验的 A+C＋TTA** 为主方案；网页提供平衡／召回工作模式和 CPU 变体；旧 clean／mosaic000 保留为历史基线与回退资产。

不能把所有阶段写成“72.81% → 78.37% → 77.19%”的同条件精度曲线：

- 72.81% 属于早期 clean 的旧标准 Val 记录。
- 78.37% 属于两轮探索后的旧 Val 召回融合方案。
- 77.19% 属于新固定协议、三种子平均的 Test 研究主方案。

它们的数据划分、评估流程、模型组合和统计口径不同，不能仅凭数值高低判断新模型比旧模型好或差。

可以采用的最终表述是：

> 项目从 YOLOv8n 训练与 Streamlit 原型出发，经早期多项模型对照选择 clean／mosaic000 候选，完成 ONNX、FastAPI、可选 DeepSeek 与 Streamlit 前后端部署；随后开展两轮精度优先调优，验证纹理微调、模型融合及 TTA 的应用价值。在披露历史探索与 C/D 水平翻转执行偏差后，进一步固定相似性分组及评估协议，从 COCO 通用预训练重新建立对照，仅使用 Train/Val 选择方案，并在冻结后统一 Test。Val 预先选定的 A+C＋TTA 研究主方案取得 Test mAP50 77.19%±0.50 个百分点、mAP50-95 44.73%±0.10 个百分点，并形成固定 seed42 的本地多模式交付。上述结果用于 NEU-DET 内部泛化评估，外部生产泛化仍待验证。

这份项目记录展示的是模型能力、实验判断、评估规范和工程落地的逐步完善。没有引入新网络结构，不自动把方法组合称为原创算法；同时不把内部测试结果当成工业现场验收。
