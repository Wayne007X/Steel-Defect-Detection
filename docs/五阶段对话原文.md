**第一阶段：YOLOv8n 初次训练与 Streamlit 原型**

基于 NEU-DET，先完成最基本的流程：**训练 → 验证 → 保存最佳权重 → 接入 Streamlit 展示检测结果**。

仓库的早期 `app.py` 直接加载 `runs/neu_defect_train/weights/best.pt`，由 Streamlit 在应用中调用 YOLO 推理，还没有独立 FastAPI 后端。这个阶段的主要成果是跑通检测原型，而不是已经选出了最佳训练方案。[早期应用代码](https://github.com/Wayne007X/Steel-Defect-Detection/blob/main/app.py)

这份早期模型还涉及后来发现的数据整理问题，因此应作为历史原型保留，不与纠正数据后的 clean／mosaic000 作公平性能对比。

**第二阶段：早期模型调优与多项对照，确定 clean／mosaic000 的角色**

基于纠正后的数据和原 **1,440／360** 划分，开展 Mosaic、模型规模、输入尺寸、损失权重、采样及学习率等探索。仓库确实记录了很多实验，例如：

- Mosaic：1.0、0.5、0。
- YOLOv8n 与 YOLOv8s。
- 640／800 输入及相关微调。
- cls、box 权重、龟裂加权采样和优化器／学习率调整。

这些实验中，部分是受控对照，部分同时改变了多个因素，报告应分别标注。[早期实验索引](https://github.com/Wayne007X/Steel-Defect-Detection/blob/main/experiments/neu_det_tuning/EXPERIMENT_INDEX.md)

主要候选的标准验证结果是：

- **clean**：mAP50 **72.81%**，mAP50-95 **38.44%**，Recall **64.95%**。
- **mosaic000**：mAP50 **72.60%**，mAP50-95 **37.84%**，Recall **68.86%**。

**最终选择依据：** clean 保留为整体 mAP 基线；mosaic000 因召回较高，成为偏向减少漏检的应用候选。其他探索没有提供足够证据替换这两个候选，也没有支持直接换成更大的模型。

**第三阶段：ONNX＋FastAPI＋DeepSeek＋Streamlit，完成前后端部署**

基于第二阶段保留的 **mosaic000**，将 `best.pt` 导出为 ONNX，再搭建独立推理 API 和网页前端。

这里选择 mosaic000 有两层依据：

- **模型层面**：前期比较中召回更高，符合当时偏向减少漏检的目标。
- **工程层面**：ONNX 已能运行 CPU 推理，同条件 `predict()` 检测框数值对照接近，支持继续做服务集成。

但当时 PyTorch／ONNX 的原生 `val()` 指标仍有差异。仓库明确把它保留为限制，**没有把“导出成功、接口可用”说成“全部精度已完全一致”**。[ONNX 与部署决策记录](https://github.com/Wayne007X/Steel-Defect-Detection/blob/main/onnx_fast_api_streamlit_docs/MOSAIC000_ONNX_导出与验证排查记录_补充部署决策.md)

这个阶段的成果是：

- ONNX Runtime 执行视觉推理。
- FastAPI 返回结构化检测结果。
- Streamlit 上传、调用接口并展示。
- DeepSeek 作为本地可选辅助分析，读取检测 JSON。
- 云端提供纯视觉检测，关闭 AI 调用。

**这是应用架构与部署阶段，不是又得到了一套更高分的新训练权重。**

**第四阶段：两轮精度优先调优，形成融合与 TTA 方案**

在已有 clean／mosaic000 权重和旧划分上，继续追求检测精度：

第一轮统一评估口径，从旧 mosaic000 微调得到纹理模型，再比较融合和 TTA；第二轮验证种子稳定性、弱类错误和类别差异化 NMS，并停止未通过验收的亮度归一化方案。

主要结果：

- **纹理单模型 seed42**：旧 Val mAP50 **72.54%**。
- **clean＋纹理模型＋TTA，平衡方案**：**76.71%**。
- **相同模型，召回后处理方案**：**78.37%**。

**最终选择依据：** 纹理微调通过预设门槛，融合／TTA 提供额外收益；但召回方案多检出 14 个目标的同时增加 32 个误报，所以保留平衡模式，召回模式作为可选项。

这里仍是反复参与选型的**旧 Val 探索成绩**。

**第五阶段：新协议、受控重训、统一 Test 与新版工程落地**

为了让结论更可复核，重新审计、人工分组并固定 **1,081／360／359** 划分，从官方 COCO 通用预训练重新建立 A／B 基线，再训练 C／D 微调对照。

三个种子的平均 Val AP50：

- A：**71.78%**
- B：**70.77%**
- C：**73.05%**
- D：**72.06%**

随后按预登记规则选择融合、TTA 和后处理，**先在 Val 选定并冻结，再统一开封 Test**。

最终研究主方案为 **A+C＋TTA、NMS 0.70**，Test 结果：

- mAP50：**77.19% ± 0.50 个百分点**
- mAP50-95：**44.73% ± 0.10 个百分点**

C／D 的水平翻转执行偏差已在 Test 前披露。网页固定使用 seed42，提供 GPU 平衡／召回、CPU 无 TTA 选项和旧模型回退；不把三种子均值直接当成网页实例的成绩。

因此，项目应该呈现为：

**训练与网页原型 → 多项模型对照 → 前后端部署 → 两轮精度提升探索 → 固定协议重训、Test 与新版交付。**

这样既保留了你最初从零搭建应用的过程，也能讲清楚后来的模型选择、评估规范和工程升级。**各阶段的成果不是只用一个最高分串起来，而是分别说明解决了什么问题、凭什么作出选择。**
