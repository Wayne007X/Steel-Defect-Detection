## 3. 遇到的主要问题

### 问题一：PyTorch 与 ONNX 的验证指标不一致

早期验证中，`mosaic000` 的标准验证结果大致如下：

  后端         Precision       Recall        mAP50     mAP50-95
  --------- ------------ ------------ ------------ ------------
  PyTorch     0.663 左右   0.689 左右   0.726 左右   0.378 左右
  ONNX        0.665 左右   0.673 左右   0.702 左右   0.361 左右

这带来了核心疑问：如果 ONNX 是从同一个 `best.pt`
导出的，为什么验证指标仍有差异？

这个问题值得解决，因为如果不区分模型本身、导出过程和评估流程，就可能错误地判断
ONNX 导出失败，或错误地把不同评估条件下的数字写进正式报告。

### 问题二：最初的检测框对照使用了不同设备

最早的一次对照使用了 PyTorch GPU、ONNX CPU。`mosaic000` 的日志显示：

-   PyTorch 检测框：22,423
-   ONNX 检测框：22,412
-   同类别且 IoU 达到匹配阈值的匹配框：22,400
-   平均匹配 IoU：约 0.99947
-   匹配框平均置信度绝对差：约 0.0000228

这说明大部分匹配检测框的位置非常接近，但当时设备不同，因此不能把速度直接当作同硬件对比结果；少量检测框差异也需要进一步控制条件检查。

### 问题三：自定义统一评估器与 Ultralytics 原生验证结果不一致

早期脚本自己实现了评估指标计算。其结果与 `model.val()`
的原生验证指标出现了明显差距。例如某次自定义评估中，`mosaic000` 的 mAP50
约为 0.488，而原生验证约为 0.726。

这类差距远大于一般的小数舍入误差。它说明自定义评估流程与 Ultralytics
原生评估流程并不等价，不能直接拿自定义评估结果替代正式的原生验证指标。

因此，后续不再将这套自定义评估器作为最终报告的权威指标来源。

### 问题四：`predict()` 与原生 `val()` 的预测结果存在差异

一次针对 `mosaic000` 的路径核查发现：

-   PyTorch `predict()` 检测框数为 22,413，而捕获到的原生验证检测框数为
    16,071；按当次脚本的匹配方式，只有 12,955 个匹配。
-   ONNX `predict()` 检测框数为 22,412，而捕获到的原生验证检测框数为
    22,947；当次匹配数为 22,409。

这表明两种 API 路径捕获到的预测集合可能不同，尤其是 PyTorch
侧的差异很大。它进一步说明：不能把 `predict()` 输出简单当作 `val()`
实际评估的预测集合，再据此断言原生验证器算错。

该检查帮助我们确认了诊断方向，但**单凭这份检测框对照，还不能完整解释原生验证指标差异的全部内部原因**。

## 4. 如何逐步排查

### 4.1 先完成导出并确认运行环境

切换到正确的 `yolo_workspace` 虚拟环境，完成两个模型的 ONNX
导出。导出日志和文件大小均确认文件生成成功。

### 4.2 将 PyTorch 与 ONNX 放到同一设备条件下检查

之后运行 CPU 对 CPU 的一致性对照。`mosaic000` 的结果为：

  项目                       PyTorch             ONNX
  ------------------------ --------- ----------------
  检测框总数                  22,413           22,412
  匹配检测框                  22,412           22,412
  未匹配检测框                     1                0
  平均匹配 IoU                    \-     约 0.9999881
  匹配框平均置信度绝对差          \-   约 0.000000099

这里的匹配采用当次脚本设定的同类别、IoU 阈值 0.5 规则。

结果说明：在该次 `predict()`
检测框对照条件下，两个后端的检测结果几乎完全一致。它是 ONNX
转换数值一致性的有力证据，但不等于两套验证 API
的所有后处理与指标统计过程都相同。

### 4.3 将原生 `model.val()` 作为正式指标来源

后续专门针对 `mosaic000` 运行原生验证：

-   PyTorch：`runs\neu_defect_mosaic000\weights\best.pt`
-   ONNX：`runs\neu_defect_mosaic000\weights\best.onnx`
-   数据配置：`D:\yolov8\NEU-DET\data.yaml`
-   图片数：360
-   图像尺寸：640
-   `conf=0.001`
-   `iou=0.7`
-   `max_det=300`
-   `batch=1`
-   `device=cpu`
-   `workers=0`

脚本不训练、不导出模型，也不自行计算 AP；它调用 Ultralytics 原生
`model.val()`
并保存两种后端的验证结果。这使报告来源更加明确，也避免继续用未经确认等价的自定义评估器替代官方验证结果。

### 4.4 检查 `rect` 参数，但没有证据表明它解决了指标差异

后来分别运行了标记为 `rect=False` 和 `rect=True`
的最终验证脚本。两次日志中，`mosaic000` 的核心结果均显示：

-   PyTorch：mAP50 约 0.726，mAP50-95 约 0.378
-   ONNX：mAP50 约 0.702，mAP50-95 约 0.361

因此，根据当前提供的两次日志，**不能得出"将 `rect=True` 就解决了 ONNX
指标差异"的结论**。此前关于 `rect`
已恢复指标的解释不够严谨；本记录以实际日志为准。

`rect`
检查仍有参考价值，但当前证据没有证明它是导致差异的根因，也没有证明它能消除差异。

### 4.5 处理 ONNX Runtime 的自动安装提示

日志中曾出现 Ultralytics 尝试安装 `onnxruntime-gpu`，随后提示安装失败或
CUDA Execution Provider 不可用，并回退到 `CPUExecutionProvider`。

当次 ONNX 验证仍继续执行并输出指标。因此，该提示不是 ONNX
文件导出失败，也不是这次 CPU 验证未完成的证据。当前环境已经能使用 ONNX
Runtime CPU provider，不应仅为消除提示而盲目更换运行时。

## 6. 目前问题是否彻底解决？

**ONNX 导出和运行已经完成，但"为什么原生验证的 PyTorch 与 ONNX
指标不同"还没有被完全解释。**

当前最可靠的处理方式是：

-   以原生 `model.val()` 输出作为对应后端的正式验证指标；
-   保留 PyTorch 与 ONNX
    各自的结果，不为了让数字一致而修改或覆盖原报告；
-   不再使用先前自定义评估器的指标作为正式结论；
-   不因自动安装 `onnxruntime-gpu` 的提示而认定 ONNX 失败；
-   后续若要继续追根因，应直接对照 Ultralytics 8.4.177
    的验证器实现及实际送入评估器的预测结果，而不是继续盲目切换参数或重复完整推理。

本阶段完成了 `mosaic000` 从 PyTorch 到 ONNX 的导出、CPU

## 9. 这一大波流程的意义：我们实际确认了什么

回顾整个过程，虽然中间多次更换诊断脚本、重复运行验证，但这些工作并非毫无意义。它们分别回答了不同层面的问题，不能把它们混成一个"ONNX
是否对齐"的问题。

### 9.1 确认 ONNX 文件可以生成并运行

`mosaic000` 的 `best.onnx` 已成功导出，后续也能通过 ONNX Runtime 的
`CPUExecutionProvider`
完成预测和原生验证。这证明文件不是一个无法加载或无法推理的导出产物。

运行日志中出现的 `onnxruntime-gpu` 自动安装提示，以及 CUDA Execution
Provider 不可用的警告，不代表 ONNX 文件本身导出失败。当前实际使用的是
CPU provider。

### 9.2 获得了 PyTorch 与 ONNX 预测输出高度一致的证据

在同一批 360 张验证图片、同为 CPU 的 `predict()` 对照中：

-   PyTorch 检测框数：22,413；
-   ONNX 检测框数：22,412；
-   按当次脚本的同类别、IoU 阈值 0.5 规则匹配：22,412 个；
-   平均匹配 IoU：约 0.999988；
-   匹配框平均置信度绝对差：约 (9.93`\times10`{=tex}\^{-8})。

这是一项重要结果：在该次 `predict()`
对照条件下，两个后端的检测框位置和置信度几乎一致。它支持"ONNX
转换后的预测数值高度接近 PyTorch"的判断。

但必须保留边界：这不等于所有 API
路径、所有预处理设置和所有评估统计过程都已经证明完全相同。尤其是原生
`model.val()` 的整体指标仍存在差距。

### 9.3 找到了不应继续使用自定义评估器作为正式指标的原因

自定义统一评估器曾给出与 Ultralytics 原生 `model.val()`
明显不同的指标。后来进一步检查发现，`predict()`
捕获的预测集合与原生验证路径中的预测集合也可能不同。

因此，不能只因为自定义评估器对 PyTorch 和 ONNX
算出的数值接近，就认为它已经完整复刻了 Ultralytics
的原生验证逻辑。此前的工作让我们明确了正式报告应采用哪套指标口径，避免把自定义评估结果误写成官方验证结果。

### 9.4 确定了哪些事情不必再反复做

截至本记录：

-   不需要为了这次指标差异重新训练模型；
-   不需要仅为了追求指标相同而重新导出 ONNX；
-   不再把自定义评估器的 mAP 作为最终报告依据；
-   不再无目的地反复切换 `rect` 等参数；
-   如果后续没有明确的验收要求强制要求解释原生验证差异，就可以先停止这轮诊断，把工作转向部署集成。

**因此，这一轮工作的实际价值是：确认 ONNX
可运行、获得预测输出高度一致的证据、发现评估口径不能混用，并明确后续部署应采用的验证和记录方式。**
它没有证明所有指标差异都已解决，但也没有证据要求我们推翻模型或重新训练。

## 10. 下一阶段决策：使用 mosaic000 ONNX 接入 FastAPI 和 Streamlit

### 10.1 是否使用 `mosaic000` 的 ONNX？

**可以把 `neu_defect_mosaic000/weights/best.onnx` 作为下一阶段 FastAPI
推理服务的候选部署模型。**

当前路径：

``` text
E:\yolo_project\runs\neu_defect_mosaic000\weights\best.onnx
```

这是一个基于现有导出和推理对照结果作出的工程选择，不代表已经证明 PyTorch
与 ONNX 的全部原生验证指标完全一致。正式记录中仍应保留：PyTorch 原生验证
mAP50 约为 0.726，ONNX 约为 0.702；mAP50-95 分别约为 0.378 和
0.361。这个差异目前尚未被彻底解释。

如果项目验收要求 ONNX 必须达到某个明确的 mAP 阈值，应先用该阈值判断 ONNX
是否合格；不能仅凭预测框一致性就跳过验收。若当前阶段的目标是搭建应用并验证在线推理链路，则可以继续集成，同时保留这项指标差异作为已知限制。

### 10.2 这一阶段不再把评估器调试作为主线

后续应区分三个职责：

  -------------------------------------------------------------------------------------------
  部分              主要职责                                   不负责的事情
  ----------------- ------------------------------------------ ------------------------------
  ONNX Runtime /    接收图片、执行 ONNX                        不在每次在线请求中计算验证集
  FastAPI           推理、后处理并返回检测结果                 mAP

  Streamlit         图片上传、调用                             不自行重复实现模型评估逻辑
                    API、展示缺陷框、类别和置信度

  离线验证脚本      使用固定验证集和指定评估口径记录模型指标   不进入普通在线推理请求路径
  -------------------------------------------------------------------------------------------

建议将预测缓存和验证报告保留为离线产物。如果以后确实需要自定义评估器，应优先复用已安装版本
Ultralytics 的评估核心，而不是继续手写一套未经验证的 AP 计算逻辑。

### 10.3 部署前只做有明确目标的回归测试

接入 FastAPI 和 Streamlit 后，选择一组固定图片作为回归样本，至少检查：

1.  API 能否稳定加载 `best.onnx` 并完成推理；
2.  预处理尺寸、颜色通道、归一化方式是否正确；
3.  返回的边界框坐标是否正确映射回原图；
4.  类别 ID、类别名称和置信度是否正确；
5.  同一张图片重复推理时，结果是否稳定；
6.  将 API 返回结果与已验证的 ONNX `predict()`
    结果进行对照，确认服务端封装没有引入新的偏差。

这组测试用于验证**部署代码和推理链路**，与之前的验证集 mAP
对照是不同任务。通过回归测试也不能据此宣称原生 `val()`
的指标差异已经得到解释。

### 10.4 建议的最终工程流程

``` text
mosaic000 best.onnx
        |
        v
FastAPI + ONNX Runtime
图片输入 -> 预处理 -> 推理 -> 后处理 -> JSON 检测结果
        |
        v
Streamlit
图片上传 -> 调用 FastAPI -> 可视化检测框和类别/置信度

离线独立流程：
NEU-DET 验证集 -> Ultralytics 原生 model.val() -> 保存正式验证报告
```

在线推理和离线评估分开后，页面刷新或用户上传图片不会触发完整验证集评估；正式指标也有固定来源，方便记录和复核。

## 12. 本阶段工作的意义与下一步原则

所以，刚刚这一大波流程的意义，就是让我们在部署前确认了模型能否导出、预测是否一致、哪些指标可信，以及哪些问题不能误判。

这些工作已经有了实际成果：

-   确认 `mosaic000` 的 ONNX 可以成功导出并正常运行；
-   通过同一批验证图片的对照，获得了 PyTorch 与 ONNX
    预测输出高度一致的证据；
-   明确正式验证指标应以 Ultralytics 原生 `model.val()` 为准；
-   识别出自定义评估器与原生验证流程存在差异，避免误用自定义指标；
-   如实记录了 PyTorch 与 ONNX
    原生验证指标仍有差距这一尚未彻底解释的问题。

因此，不需要为了追求每个小数完全一致而无限延长排查。当前证据足以支持进入下一阶段的工程集成，但不能把尚未解释的指标差异描述为已经解决。

**下一步应该把已经取得的成果真正用起来，而不是继续陷在评估器里。**
工作重点转向使用 `mosaic000` 的 `best.onnx` 接入 FastAPI 和
Streamlit，并通过固定样本回归测试确认服务端预处理、推理、坐标映射和结果返回正确。模型正式指标继续引用原生验证报告；只有出现新的部署异常或明确的验收要求时，再针对具体问题开展进一步诊断。
